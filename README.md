# CST 中文界面插件与便携启动器

为 **CST Studio Suite 2025（Windows x64）** 提供中文界面辅助显示，包括功能区、菜单、部分对话框、导航树固定分类，以及工程模板向导中的部分网页内容。

项目提供可直接运行的中文启动器，也保留插件源码、翻译词库和测试代码，方便继续补充翻译、修正专业术语和适配更多界面。

> **当前属于持续完善中的测试项目，尚未实现 CST 全部界面的完整汉化。**
>
> 使用前请保存工程。使用者需要自行安装并正常授权 CST。本仓库不包含 CST 主程序、许可证、破解工具或厂商运行库。

## 可以做什么

目前主要覆盖：

- 功能区页签、分组及部分按钮。
- 已收录的下拉菜单、右键菜单及操作提示。
- 部分标准 Qt 和 Windows 对话框。
- 导航树中的固定系统分类。
- 工程模板向导中的部分标题、选项、按钮和路径导航。
- 用户自定义词库对部分控件译文的补充和覆盖。

当前代码包含约 **1510 条控件翻译词条**，以及 **210 条工程模板向导专用词条**。

这些数字表示词库规模，**不是整个 CST 的汉化率**。即使某个词条已存在，也可能因为控件类型、显示方式或所在模块尚未适配而继续显示英文。

## 使用方法

1. 点击仓库页面的 **Code → Download ZIP**。
2. 将 ZIP 完整解压到本地文件夹。
3. 双击 `CstChineseLauncher.exe`，也可以运行 `start-zh.cmd`。
4. 如果没有自动找到 CST，点击“选择程序…”，选择：

   ```text
   <CST 安装目录>\AMD64\CST DESIGN ENVIRONMENT_AMD64.exe
   ```

5. 点击“启动中文版”，等待 CST 打开。

请完整保留启动器旁边的 `CSTRibbonZh` 文件夹，不要只复制一个 EXE。

插件仅作用于通过中文入口新启动的 CST 实例。已经运行的 CST 不会自动更新语言或热加载新版 DLL。

### 是否需要安装编译环境？

普通使用者不需要安装 Visual Studio、C++ 编译器或 Qt SDK，直接使用仓库中的编译成品即可。

只有修改 C++ 源码并重新构建插件时，才需要这些开发依赖。

### 是否可以搬到其他电脑？

可以移动或复制整个插件文件夹。

在另一台电脑上使用时，需要选择那台电脑上已经安装的 CST。启动器会检查主程序和相关运行库，但静态检查通过不代表所有操作都已经验证兼容。

### 设置保存在哪里？

启动器保存的 CST 路径位于：

```text
%LOCALAPPDATA%\CST-Chinese-Portable\cst-root.txt
```

可选的个人控件词库位于：

```text
%LOCALAPPDATA%\CST-Chinese-Portable\user.tsv
```

插件文件夹不需要复制到 CST 安装目录，也不需要修改系统全局 Qt 环境变量。

## 翻译逻辑是什么？

本项目的主要流程是：

```text
读取界面原文
    ↓
判断是否属于允许翻译的控件或显示区域
    ↓
按所在界面的适配规则匹配本地词库
    ↓
将显示文字替换为中文
    ↓
监听后续界面变化，处理新出现或重新生成的内容
```

运行时主要使用预先整理的本地词库。

**目前没有通过截图 OCR 识别整个屏幕，也没有实时调用 Codex、ChatGPT 或在线机器翻译 API。** Codex 用于开发代码和辅助整理译文，插件运行时不依赖 Codex 服务。

### 1. 普通控件翻译

C++ 插件在 CST 进程内运行，读取已适配控件的显示属性，例如：

- 按钮和菜单文字。
- 窗口、分组和页签标题。
- 工具提示和状态提示。
- 部分标签及输入框的占位提示。

匹配时会处理部分换行、空白、大小写、快捷键标记和标点差异。

插件也会监听控件显示、动作变化等事件，并定期检查已登记的控件。因此，点击以后才出现的界面也有机会被翻译。

但这需要同时满足两个条件：

1. 对应控件的显示方式已经适配。
2. 本地词库包含适用的译文。

### 2. 导航树翻译

导航树中的一些名称属于工程模型数据，不能简单改写。

因此，插件对已识别的固定分类采用显示层处理：在绘制界面时显示中文，保留底层原始名称。

例如，界面中的系统分类可以显示为“材料”，而程序内部仍保留其原始分类数据。

用户自己创建的对象名称、工程内容和未确认用途的数据节点，不进行无差别替换。

由于底层数据保留原值，复制、脚本或辅助功能接口仍可能读到英文名称。

### 3. 工程模板网页向导翻译

CST 的部分向导使用内嵌网页显示，普通 Qt 按钮翻译逻辑无法直接覆盖这些内容。

项目为本机安装目录中的工程模板页面增加了专用适配：

```text
Library/ConfigurationWizard/index.html
```

插件通过 Qt WebEngine 的脚本执行接口，在隔离的 JavaScript 环境中处理指定显示区域，并监听页面动态变化。

处理对象包括已适配的标题、工作流程名称和按钮文字。不会直接修改：

- 原始工作流程数据对象。
- 选项编号。
- 链接目标。
- 用户输入值。
- 单位值。
- CST 安装目录中的厂商网页文件。

该适配依赖 CST 2025 所使用的 Qt 5.15 MSVC x64 接口，不能直接视为适用于其他版本。

### 4. Windows 原生控件翻译

对部分 Windows 原生对话框，插件采用单独的控件遍历逻辑，处理限定范围内的静态文字和按钮。

并不是所有原生、自绘或第三方窗口都已经适配。

## 术语如何确定？

翻译应符合电磁仿真、三维建模和工程软件的使用习惯，不能只按单词逐字替换。

部分示例：

| 英文 | 当前采用的中文 | 使用语境 |
|---|---|---|
| Orthographic | 正交投影 | 三维视图 |
| Cutting Plane | 剖切平面 | 模型剖切显示 |
| Dimension | 尺寸标注 | 绘图与测量 |
| Pick | 拾取 | 几何对象选择 |
| Field Import | 导入场数据 | 场数据输入 |
| Voltage Monitor | 电压监视器 | 仿真监视器 |
| Current Monitor | 电流监视器 | 仿真监视器 |
| Normal | 法向 | 剖切平面设置 |
| Intersection Check | 相交检查 | 几何检查 |

同一个英文单词在不同位置可能需要不同译法。例如，剖切设置中的 `Normal` 表示“法向”，不能把这个译法直接用于所有出现 `Normal` 的地方。

现有实现中仍有通用词库匹配，后续需要继续补充上下文限定和专业术语校对。

## 如何修改翻译？

### 情况一：补充普通控件词条

修改：

```text
src/CSTRibbonZh/i18n/*.tsv
```

每行格式为：

```text
英文原文<TAB>中文译文
```

其中 `<TAB>` 必须是真正的制表符，不是几个空格。

示例：

```tsv
Voltage Monitor	电压监视器
Current Monitor	电流监视器
Orthographic	正交投影
```

注意：

- 使用 UTF-8 编码。
- 避免增加重复键；已有条目应修改原条目。
- 保留 `%1`、`%2`、`%s` 等参数占位符。
- 不要把路径、表达式、单位值和用户对象名称作为普通界面文字替换。
- 修改内置词库后，需要重新编译插件。

校验命令：

```powershell
python ./src/CSTRibbonZh/tools/check_catalog.py
```

也可以先使用个人 `user.tsv` 补充或覆盖控件词条，然后重新启动 CST。个人词库不会自动解决未适配控件的问题，也不用于覆盖独立的网页向导 JSON 词库。

### 情况二：修改模板向导翻译

修改：

```text
src/CSTRibbonZh/web/wizard-zh.json
```

示例：

```json
{
  "Create Project Template": "创建工程模板",
  "Antennas": "天线",
  "Solvers": "求解器"
}
```

新增内容如果位于未覆盖的网页区域，还需要修改：

```text
src/CSTRibbonZh/web/wizard.js
```

这里定义允许处理的显示区域以及动态更新逻辑。

不要为了扩大覆盖范围，直接翻译页面里的所有文字节点，更不要修改输入框值、内部编号或页面脚本。修改后需要重新编译插件。

### 情况三：词库里已有译文，界面仍然是英文

这通常需要检查控件适配，而不是继续重复添加词条。

建议按以下顺序排查：

1. 是否通过正确的中文启动器启动了新实例？
2. 当前实例是否加载了最新 DLL？
3. 实际原文是否包含换行、快捷键标记或其他差异？
4. 该界面属于普通 Qt 控件、导航树、原生窗口，还是网页？
5. 控件是否被现有规则判断为用户数据并跳过？
6. 文字是否由另一个属性缓存，或在翻译后被 CST 重新生成？

根据结果修改：

- 普通控件：`surface.cpp`
- 控件跟踪与生命周期：`ribbonplugin.cpp`
- 原生对话框：`nativeui.cpp`
- 网页向导：`webui.cpp`、`web/wizard.js`

修改过滤条件时应尽量限定到已经确认的界面或命令，避免影响同名的用户数据。

## 如何重新编译？

### 构建启动器

需要 Windows 上的 .NET Framework C# 编译环境：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ./tools/build-launcher.ps1 -Test
```

### 构建 C++ 插件

需要：

- MSVC x64 编译器。
- Windows SDK。
- Qt 5.15 MSVC x64 SDK。
- 本机 CST 2025 安装及其运行库。

执行：

```powershell
./src/CSTRibbonZh/build.ps1 `
  -Verify `
  -CstRoot "<CST安装目录>" `
  -QtSdk "<Qt SDK目录>"
```

构建和测试通过后，先退出使用旧插件的 CST，再复制新 DLL：

```powershell
Copy-Item `
  ./src/CSTRibbonZh/plugins/generic/CstRibbonZh.dll `
  ./CSTRibbonZh/plugins/generic/CstRibbonZh.dll `
  -Force
```

重新通过中文入口启动 CST，核对实际界面。

### 重新打包

```powershell
python ./tools/package.py --output "./CST-Chinese-Portable.zip"
```

打包工具按白名单收集文件，并生成校验清单。构建临时目录、个人词库和机器诊断日志不应作为发布内容上传。

## 测试与稳定性

项目已有针对下列行为的测试：

- 启动路径与兼容性检查。
- 翻译词库格式和占位符。
- 菜单、按钮、页签及动态控件。
- 导航树显示与原始模型数据保持。
- 命令编号、按钮触发及勾选状态。
- 部分控件销毁和插件退出清理。
- 发布包完整性。

针对一次实际崩溃，已修复退出清理阶段访问失效控件指针的问题。专门的对照测试能够触发旧代码的访问异常，修复后的代码通过了连续清理回归。

这些测试不能代替真实 CST 中的完整工作流程验收。网页浏览器自动回归、长时间使用，以及所有求解器和第三方模块的验证仍不完整。

详细状态以 `TEST_RESULTS.md` 为准。

## 已知限制

- 尚未实现整个 CST 的完整汉化。
- 部分深层菜单、求解器说明、动态日志和错误提示仍可能显示英文。
- 自绘界面、第三方模块及帮助文档尚未全面适配。
- 某些术语仍需要结合实际功能继续校对。
- 中文显示可能存在截断、布局或高 DPI 问题。
- 已通过测试不代表不存在崩溃或其他缺陷。
- 目前主要针对 CST 2025 x64，其他版本需要单独适配和验证。
